# Email Audience and Product Broadcast Plan

## Purpose

Add an admin-managed email audience system built from existing paid customer emails, then add product-specific broadcast email for newly added products.

This feature has two separate purposes:

1. Preserve transactional order email for recovery and audit.
2. Create a manageable admin audience list for outbound product announcements.

The existing `orders.customerContact` field must remain the source of truth for order recovery. The new audience feature must not directly repurpose or overwrite historical order data.

## Why This Must Be a Separate System

Current order emails are part of transaction history and are already used for:

- order recovery
- admin order search
- order confirmation email

The new requirements add list management actions that do not fit safely on raw orders:

- edit an email
- delete an email from the list
- export all emails
- exclude emails from future broadcast
- broadcast only for a specific product

If those actions mutate `orders.customerContact`, the app will lose reliable recovery history and auditability. For that reason, implementation must introduce a separate audience collection derived from paid orders.

## Scope

In scope for this plan:

- admin menu for audience management
- automatic audience sync from paid orders
- backfill of existing paid-order emails
- list/search/filter audience emails
- edit audience email
- delete audience email from audience list
- export audience emails
- product-specific broadcast flow
- fixed-template product announcement email
- test send
- admin password confirmation for live broadcast
- send logging

Out of scope for this plan:

- unsubscribe link in outbound email
- HTML email rendering
- AI-generated sales copy
- background queue workers
- retry dashboard for failed broadcast sends
- editing historical order email values

## Product Rules

The implementation agent must preserve these rules:

- Only `PAID` orders can feed the audience.
- Do not ingest `PENDING` or `EXPIRED` orders into the audience.
- Normalize all emails with `trim().toLowerCase()`.
- Ignore empty or invalid emails.
- Ignore known test email `customer@example.com`.
- Normalize future `orders.customerContact` writes before storing them.
- Audience edits/deletes affect the audience list only, not historical orders.
- Live broadcast requires both admin session and password confirmation.
- Test send uses the exact same subject/body builder as live send.
- Broadcast copy must be fixed-template text plus a short manual teaser, not generated by AI.
- `Delete` is list removal only. `Exclude` is the suppression action for no-broadcast behavior.
- If a paid order email is corrected later, audience sync must move or reconcile the existing audience row instead of leaving the old wrong address active.

## Data Model

### 1. Audience collection

Create a new Mongo collection named `audiences`.

Recommended interface:

```ts
export interface AudienceContact {
  _id?: ObjectId;
  email: string; // canonical active send target, normalized
  aliases: string[]; // historical normalized emails linked to this audience row
  allEmails: string[]; // [email, ...aliases], normalized, unique across the whole collection
  source: "ORDER";
  status: "ACTIVE" | "EXCLUDED" | "BOUNCED";
  notes?: string;
  lastBroadcastAt?: Date;
  deletedAt?: Date;
  restoredAt?: Date;
  createdAt: Date;
  updatedAt: Date;
}
```

Why `aliases` and `allEmails` are required:

- user wants edit email
- past orders will still contain the old email
- future matching and buyer exclusion must still recognize that old address
- uniqueness must apply to canonical emails and aliases, not only canonical emails

Edit behavior:

- when admin edits `email`, move the previous canonical `email` into `aliases`
- keep `aliases` unique and normalized
- recompute `allEmails` as canonical email plus aliases
- reject edit if another audience row already contains the target email anywhere in `allEmails`

Delete behavior:

- implement as soft delete with `deletedAt`
- do not hard delete in V1
- hide deleted records by default from the list
- do not broadcast to deleted records
- if a future paid order matches a deleted audience row, clear `deletedAt` and restore the same row
- delete is not the same as exclude; excluded contacts stay visible and intentionally suppressed

Metrics behavior:

- do not persist mutable aggregate counters like `totalPaidOrders` as source-of-truth fields in `audiences`
- compute audience stats from `orders` at query/export time
- this avoids double-counting during backfill, retries, or contact updates on paid orders

### 2. Broadcast log collection

Create a new Mongo collection named `broadcasts`.

Recommended interface:

```ts
export interface ProductBroadcastLog {
  _id?: ObjectId;
  mode: "TEST" | "LIVE";
  productId: ObjectId;
  productSlug: string;
  productTitle: string;
  subject: string;
  teaser: string;
  recipientCount: number;
  sentCount: number;
  failedCount: number;
  recipientsSample?: string[];
  status: "COMPLETED" | "PARTIAL" | "FAILED";
  requestedBy: "ADMIN";
  createdAt: Date;
  completedAt?: Date;
}
```

V1 does not need a history UI, but the log collection is required for audit and support.

## API Surface

### Audience APIs

Create admin-only routes:

- `GET /api/admin/audience`
- `PATCH /api/admin/audience/[id]`
- `DELETE /api/admin/audience/[id]`
- `GET /api/admin/audience/export`

Recommended behavior:

- `GET /api/admin/audience`
  - supports `search`, `status`, `page`, `pageSize`
  - `search` must match canonical email and aliases
  - default excludes rows where `deletedAt` is set
  - returns paginated rows and total count
  - returns derived order stats for each row
- `PATCH /api/admin/audience/[id]`
  - allows editing `email`, `status`, and `notes`
  - validates normalized unique target email
  - preserves alias chain and recomputes `allEmails`
- `DELETE /api/admin/audience/[id]`
  - performs soft delete only
- `GET /api/admin/audience/export`
  - returns CSV
  - default export excludes rows where `deletedAt` is set
  - support optional `includeDeleted=1`

### Broadcast APIs

Create admin-only routes:

- `POST /api/admin/broadcast/test`
- `POST /api/admin/broadcast/live`

Recommended behavior:

- `POST /api/admin/broadcast/test`
  - input: `productId` or `slug`, `teaser`, `targetEmail`
  - validates product exists
  - builds the exact same subject/body as live broadcast
  - sends to one address only
  - logs mode `TEST`
- `POST /api/admin/broadcast/live`
  - input: `productId` or `slug`, `teaser`, `adminPassword`
  - validates admin session
  - validates password against current admin password
  - computes recipients from `audiences`
  - excludes audience rows with status not equal to `ACTIVE`
  - excludes customers who already bought the same product
  - sends in batches
  - logs final counts and status

## Template Rules

Do not generate marketing copy dynamically.

The email must use:

- fixed Indonesian subject
- fixed Indonesian body structure
- one short manual teaser entered by admin

Recommended constraints:

- teaser is required
- teaser length: 10 to 160 characters
- plain text only
- no HTML

Recommended template:

Subject:

```text
Baru tersedia: {productTitle}
```

Body:

```text
Halo,

{productTitle} baru saja tersedia.

{manualTeaser}

Lihat detailnya di sini:
{productUrl}

Kalau cocok, langsung cek sekarang.
```

The implementation must not auto-insert hype phrases, fake urgency, or AI-style filler.

## Broadcast Recipient Rules

Live broadcast recipients must be computed from `audiences`, not raw orders.

Include only:

- `status === "ACTIVE"`

Exclude:

- `EXCLUDED`
- `BOUNCED`
- rows where `deletedAt` is set
- recipients who already bought the same product

Buyer exclusion logic must account for edited emails:

- query all `PAID` orders for the product
- normalize `customerContact`
- create a set of buyer emails
- exclude an audience row if its canonical `email` is in the set
- also exclude if any value in `aliases` is in the set

## Send Strategy

Do not implement a background queue in V1.

Use a synchronous batched send with a safety cap:

- default max live recipients per request: 100
- default batch size: 10
- continue on per-recipient error
- collect `sentCount`, `failedCount`, and sample failures for logs

Make both values configurable:

- `BROADCAST_MAX_RECIPIENTS` default `100`
- `BROADCAST_BATCH_SIZE` default `10`

If recipient count exceeds the configured max:

- reject the request
- show a clear admin error
- require a narrower audience strategy in a later phase

## Security Rules

Broadcast is higher risk than order confirmation, so add stricter controls.

Required protections:

- admin session check on all new admin routes
- explicit password confirmation on live broadcast route
- dedicated rate limit for live send
- dedicated rate limit for test send
- no recipient list sent to client until server computes it
- do not expose full failure traces to browser
- use constant-time password comparison inside the verification helper

Add new rate limits in `lib/rateLimit.ts`:

- `AUDIENCE_EXPORT`
- `BROADCAST_TEST`
- `BROADCAST_LIVE`

Recommended values:

- `AUDIENCE_EXPORT`: 10 per 10 minutes
- `BROADCAST_TEST`: 10 per 10 minutes
- `BROADCAST_LIVE`: 3 per 15 minutes

## Phase 2: Audience Data Layer and Migration

Objective:
Create the audience collection and make it auto-sync from paid orders.

Tasks:

- create `lib/audience.ts`
- implement `normalizeEmail`
- implement `buildAllEmails`
- implement `upsertAudienceFromPaidOrder`
- implement `reconcileAudienceForPaidOrderContactChange`
- integrate auto-sync into `lib/orders.ts` inside successful payment handling
- integrate fallback sync into `app/api/orders/route.ts` when a paid order receives/changes `customerContact`
- add a one-time script `scripts/backfill-audience.ts`
- add npm script entry for the backfill script
- update `scripts/setup-indexes.ts` with new collection indexes

Upsert rules:

- find audience row by any value in `allEmails`
- if none exists, create a new `ACTIVE` row
- if match exists, do not create a duplicate row
- if matched row is soft deleted, clear `deletedAt` and restore the same row
- if matched row is `EXCLUDED` or `BOUNCED`, keep status unchanged
- do not mutate historical order records during audience sync

Paid-order contact correction rules:

- when `orders.customerContact` changes on an already paid order, load the previous normalized email before updating the order
- if the previous email belongs to an existing audience row and the new email does not belong to another row, update that same audience row to use the new canonical email and append the old email to `aliases`
- if the new email already belongs to another audience row, do not auto-merge rows in V1; log the conflict and leave it for admin review
- after the correction path runs, there must not be two active audience rows representing the same corrected paid customer email chain

Backfill rules:

- scan existing `PAID` orders only
- normalize email
- skip invalid/test emails
- build/update audience rows deterministically through the same shared upsert helper
- script must be safe to rerun

Deliverables:

- audience data exists independently from orders
- new paid orders auto-create or update audience rows
- old paid orders can be backfilled once

Acceptance:

- creating a paid order with a valid email creates audience data
- rerunning sync does not duplicate rows
- mixed-case emails dedupe correctly
- a deleted audience row is restored if the same customer makes a new paid order later
- correcting a paid order email does not leave the old incorrect email active as a separate audience row

## Open Decisions Resolved by This Plan

These decisions should not be reopened during implementation unless blocked by code constraints:

- Use a separate `audiences` collection.
- Use soft delete via `deletedAt`, separate from send status.
- Keep historical order email unchanged.
- Use canonical email plus `aliases` plus `allEmails` uniqueness.
- Derive audience order stats from `orders` instead of storing mutable counters in `audiences`.
- Use fixed-template plain-text email.
- Require password only for live broadcast.
- Exclude prior buyers of the same product.
- Use synchronous batched send with a configurable hard cap in V1.
